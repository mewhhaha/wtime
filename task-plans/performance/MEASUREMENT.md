# Measurement protocol and decision rules

The historical [first report](../../wtime/docs/benchmarks/wasmtime-comparison.json) and [second report](../../wtime/docs/benchmarks/wasmtime-comparison-run2.json) stay immutable. They cover five synthetic MVP workloads and cannot establish GC, SIMD, thread, or continuation performance. Freeze a pre-change executable and complete core source snapshot before touching core code: the checkout has no committed historical baseline to rebuild automatically.

The historical executable exposes only its original six-argument CLI. P002 supplies a compatible single-case adapter built against the immutable archived core sources; P003 extends that adapter with typed workload setup. Rebuilding an adapter produces a separate hash/versioned artifact and never overwrites the original executable/source/reports. Use the same harness protocol/timing implementation on both sides, record adapter and frozen-core identities, and reject unavailable original APIs/policies. New reference/tier hooks are not assumed to exist in the old runtime. A new adapter's measurements are fresh frozen-core measurements, not a relabeling of the historical 21-sample run.

Before each candidate edit, archive the immediate predecessor with the command in its **Before editing** section. Use that archive to decide the incremental change, and P001's frozen original for milestone gains. If a workload needs a newer compatible adapter, build it in a new hash-bound directory against that archive's unchanged core. Native tasks supply a per-task matched portable archive command, so their comparison never consumes an uncreated or silently overwritten baseline.

## Three verification lanes

Use three separate lanes throughout the plan. **Development** uses exact changed-path semantic tests, locked incremental builds, and source-bound smoke timings. Its receipts support iteration only; they never complete or promote a task. **Candidate gates** use a task-owned, frozen selection manifest written before implementation and an immutable archive of the immediate predecessor. They compare only the declared target rows, held-out rows, protected controls, and mandatory cold controls against that predecessor. **Milestone gates** exercise the full supported workload families and interaction suite on the combined selected tier, including P001 totals; they retain exhaustive semantic, build, and performance acceptance.

A candidate manifest binds the task and source revision, targeted optimization shapes, exact workload IDs and input values, role (`target`, `held_out`, or `protected_control`), stages, feature/profile and runtime settings, baseline identity, and required cold products. The selector must resolve every ID against the current workload registry and reject missing, duplicate, role-conflicting, or stale rows. Predeclare small and large target inputs where the registry offers scaling, plus held-out inputs and controls that do not exercise the intended optimization. Any lack of a suitable registered row is an explicit gap that must be resolved in the recipe before implementation; it cannot be hidden by widening or narrowing selection after results are seen.

All task-specific meaningful correctness and regression cases remain mandatory in every lane where they apply. Candidate timing narrows only the performance rows. It does not narrow semantic coverage, fallback checks, source-fuel or cancellation checks, trap and memory oracles, optimizer corruption/budget checks, or unsupported-feature reporting. Candidate comparisons use the production binary with instrumentation off, two independent seeded runs, at least 30 complete pairs for every declared timing row in each run, and 10,000 deterministic bootstrap resamples with the existing paired-statistics rules. Primary-family and protected-control decision thresholds remain unchanged.

Every candidate recipe must freeze and verify its immediate predecessor before editing. That archive is the only baseline for the candidate promotion decision. P001's immutable original remains reserved for exhaustive milestone totals; candidate-level timing does not claim or imply P001-relative portfolio progress. Record both identities and keep their evidence separate.

## Cold-product accounting

Measure each unique Wasm/profile/runtime-configuration/stage-setup product once for preparation and first use. `cold_products.py` classifies equivalence from actual Wasm bytes, feature profile, runtime settings, and stage setup; a shared source path or workload family alone does not establish equivalence. Input-dependent setup, different feature settings, or distinct stage boundaries require separate products. `dataset_cache.py` may let aliases reference the same immutable raw pairs only when that product identity matches exactly; reports retain alias-to-product links, unique raw sample counts, and shared uncertainty. Never present reused samples as independent observations.

Candidate gates include the applicable `prepare_large` cold control and the tiny `call_overhead` `first_call` and `load_and_call` controls, along with the task's declared target and protected-control products. Keep all five standard timing stages distinct. Cold-product reuse cannot suppress an explicit workload correctness or setup/reset check.

## Required measurements

Keep `prepare`, `instantiate`, `first_call`, `warm_call`, and `load_and_call` distinct. Add optional decode/validate/type-intern/lower subphase telemetry in an instrumented run; those timings are diagnostic, not comparable production latency. Preparation compares different execution products across engines. Show engine startup/process startup separately if measured. Dynamic calls include each API's inherent result ownership cost; new buffer/typed APIs are additional explicitly labeled rows, not replacements for the original dynamic comparison.

All workloads have versioned deterministic sources, parameter ranges, independent expected outputs or a documented semantic oracle, feature requirements, engine capability results, work units, setup/reset policy, and timing boundaries. Include scalar scaling and branch shapes, direct/indirect/tail calls, narrow/wide memory accesses, bulk/growth, portable SIMD, GC/ref casts, exceptions, continuations, shared-memory contention, and a few reproducible representative kernels. Correctness checks include memory effects/traps where a scalar checksum would miss behavior. Compare equivalent work and feature policies; do not report a Wasmtime ratio for unsupported proposals.

Store raw samples plus report metadata under `target/performance/<task>/<run>/`; retain selected final evidence under `docs/benchmarks/performance/`. Runtime patches update the measured source identity and never relabel old reports as current. Archive baseline binaries locally with their source snapshot/hashes and reconstruction instructions; do not commit large binaries into the small repository.

## Paired comparisons

For shared-verifier workflows, freeze and validate the predeclared predecessor and build the candidate before timing. Run paired measurements against the already-built executables; compilation, build-budget collection, artifact copying, and compression stay outside timed observations. Keep benchmark/workload identities separate from analysis identities so changes to statistics or gate code invalidate analysis without discarding unchanged timing evidence. Use `statistics` once to produce analysis and the gate decision together. The explicit `audit-statistics` command recomputes both for comparison and may query Cargo metadata; it collects no new timings. Finalization and packaging reuse validated receipts without rerunning benchmarks when measured inputs are unchanged. Preserve all meaningful workload, correctness, and regression cases.

P002 adds a driver that launches separately built baseline and candidate wtime benchmark executables against the same bytes. It records an A/B pair ID, randomizes order with a recorded seed, uses one allowed logical CPU, calibrates warm batches, and does not build while measuring. Do not try to link two copies of the same Rust runtime into one process. Preserve the current Wasmtime comparator as an additional reference.

Use at least 30 complete paired observations in each of two fresh runs. Record hardware, CPU affinity/quota, toolchain, codegen/feature settings, seed, input, actual batch sizes, source and executable hashes, and whether the reference CPU was otherwise idle. Shared-cloud noise can make a result inconclusive. Thread measurements use independent runs with recorded worker counts, barriers, wall latency, throughput, and scheduling caveats.

Analyze paired log ratios with 10,000 deterministic bootstrap resamples and a 95% interval for the median ratio; show raw medians, MAD, p25/p75, and per-run results. Do not claim scheduler-driven request p99 from batched averages. A latency-tail task must collect actual individual latency observations. Predeclare each candidate selection in its task-owned manifest before optimizing. Run every declared target, held-out and protected-control row; milestone recipes still run the full supported family, not only its best inputs.

## Promotion rule

For a candidate intended to improve warm execution, require a point estimate of at least 5% improvement and an interval wholly below 1.00 in both runs on its declared primary family. Protected controls must have an upper regression interval <=1.05, or remain inconclusive pending a less noisy run. Report a family aggregate as an equally weighted geometric mean over predeclared workload medians, never over unlike timing stages. A larger win on one case does not erase a serious regression on another.

Default preparation and first-use controls have a <=1.25 relative preparation budget for small/large modules and <=1.05 first-use budget for the tiny one-shot case. A slower optional tier may instead be justified by measured break-even and a policy that avoids it for cold code. Absolute build/dependency ceilings in C7 remain hard. Clean/leaf/release build, RSS, stripped size, and retained code ratios above 1.25 receive explicit explanation and a simplification/packaging decision, even when below a hard ceiling. These relative gates are design choices for this new plan, not measurements already passed.

Pure contract/tooling tasks use correctness and integrity gates rather than invented speedup claims. Structural patches with no demonstrated speedup may be retained only for a separately stated necessary contract (e.g. cheap immutable payload); label them `contract_only`. Optimization candidates can finish with `adopted`, `rejected`, or `inconclusive`, with evidence and a clear next step. Do not enable an inconclusive experiment by default. Child tasks whose conditional backend was declined are `deferred`/`not_selected`, not implemented.

Break-even call count is `ceil(extra_prepare_ns / saved_warm_ns)` only when preparation costs are comparable and savings are positive and statistically supported. Include extra instance setup when relevant. If no positive savings exist, report no finite break-even. Show total latency at 1, 10, 100, and 10,000 calls and account for compilation spikes/code eviction in adaptive tiers.

Milestone aspirations are 10x faster compute after structural work, 100x after portable representation work, and within 2–10x of Wasmtime for eligible optimized code. Missing an aspiration is a result to investigate, never authorization to skip instructions, reduce workload, weaken fuel/cancellation silently, or remove support.

## Reproducible commands added by the plan

P001 adds `tools/wtime-bench/baseline.py --output DIR` (freeze/verify archive). P002 adds `baseline.py --adapt-harness HARNESS --baseline ARCHIVE --output DIR` and `compare.py --baseline DIR --candidate EXE --selection NAME --output DIR`. P016 adds `baseline.py --mode NAME` for current-source archives and `--candidate-mode NAME` to comparisons; `portable` resolves to the current selected portable policy, excluding native, and records its actual settings. Explicit quantum arrives only through P088. P003 owns `workloads.json` and named selections. P004 adds `analyze.py --input DIR --output FILE`. P005 adds `gates.py --task PNNN --comparison DIR --build FILE --output FILE` and optional `build_budget.py --features PACKAGE/FEATURE`. P007 adds `profile.py --selection NAME --output DIR`. P014 adds `tier_check.py --tier NAME --selection NAME --output DIR`; P108 adds its `selected` expansion. All use Python's standard library, reject incomplete/non-finite reports, and exit nonzero for actual errors. A capability gap is a named unsupported comparator, never a fabricated timing sample.

Candidate-selection support uses `selection_manifest.py`, `focused_compare.py`, `candidate_gate.py`, `cold_products.py`, and `dataset_cache.py`. See the [implemented workflow and exact commands](../../wtime/docs/verification/fast-performance.md). The plan checker checks tool producers/dependencies; writing a command into a task does not imply that it has executed.
