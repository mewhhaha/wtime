JS String Builtins is catalogued as affecting core and JS API. The pinned proposal adds JS import/builtin recognition and compile options, not an independent core opcode/encoding/type rule; its examples use existing GC/import instructions already covered here. Compact imports remain fully included despite their JS-string motivation.

All Phase 0–2 proposals are outside this snapshot, including Component Model, Type Imports, shared-everything threads, stringref, acquire-release atomics, FP16, relaxed dead-code validation, memory control, JS primitive builtins, C/C++ API and JIT interface. Some useful nonstandard tooling may already implement them; that does not add them to this runtime.

## Draft-specific caveats

- Custom Descriptors: core exactness and imports are specified. The “Type Section Field Deduplication” section is a bare TODO. Do not fabricate a binary format or claim it implemented. T148 tracks the source contract; a later specification change needs new tasks.
- Custom Page Sizes: inherited prose includes assumptions that need checking when combined with memory64 and one-byte pages. T085 resolves the normative width/limit rules before execution work; it must not blindly hard-code inherited 32-bit bounds.
- Stack Switching: use the pinned complete instruction set, including symmetric switch and both throwing resume variants. JSPI is excluded and is not a substitute for core continuations.
