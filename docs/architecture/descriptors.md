# Custom descriptor Core source audit

This contract is tied to [`WebAssembly/custom-descriptors` commit `4aa477a4c1ca064fe3592b3a0307509e9059d0f9`](https://github.com/WebAssembly/custom-descriptors/tree/4aa477a4c1ca064fe3592b3a0307509e9059d0f9), recorded with its root tree checksum in [spec-lock.json](spec-lock.json). The proposal repository carries an inherited `specification/wasm-3.0` tree, but that tree contains no descriptor-specific rules. The descriptor delta is described in `proposals/custom-descriptors/Overview.md`, which contains syntax, formal typing judgments, binary grammar, and execution descriptions. Treat its stated formal rules as the pinned proposal contract, and the integrated Core 3.0 spec as the baseline for unchanged Core behavior. The `test/core/custom-descriptors/` WAST files provide conformance evidence. The tests do not define semantics where the proposal leaves a TODO.

## Core rule matrix

| Rule area | Pinned rule | Test sources | Owner |
| --- | --- | --- | --- |
| `descriptor` and `describes` clauses | Clauses apply only to struct types. A descriptor type names the described type and the described type names its descriptor. Both definitions must be in one recursion group because of the mutual references. A type may have both clauses, enabling descriptor chains. Clause presence and target participate in type identity. See Overview sections “Custom Descriptor Definitions” and “Binary Format / Describes and Descriptor Clauses”. | `binary-descriptors.wast`; `descriptors.wast` | T149, T150 |
| Clause pairing and graph shape | The references must pair exactly; a type cannot describe itself or form a cycle. The proposal describes the previous-type restriction as the mechanism preventing cycles. Descriptor and described types must have matching finality. A declared subtype must preserve paired descriptor/describes edges to corresponding supertypes (the complete-square rule). | `binary-descriptors.wast`; `binary-descriptors.wast` and `descriptors.wast` | T149–T150 |
| Descriptor-related subtyping | Descriptor types subtype only corresponding descriptor types, and described types subtype only corresponding described types. Descriptor targets follow the corresponding supertype relation. Sharedness matching is described for shared-everything threads, which is outside this implementation’s scope. Do not implement shared-everything semantics from this text. | `descriptors.wast`; shared-everything behavior is excluded | T150 |
| Exact heap types | `(exact t)` is a subtype of `t`; declared subtypes of `t` are not thereby subtypes of `(exact t)`. Abstract heap types have no exact variant. Instructions producing references to defined heap types produce exact references, subject to the special exact-import rule below. | `exact.wast`, `exact-casts.wast`, `exact-func-import.wast`, `array_new_exact.wast` | T149–T153; cross-cutting GC owners T106–T120 |
| Exact function imports | Exact function import syntax distinguishes exact type imports from ordinary imports. A function imported exactly must satisfy exact function typing; exports do not carry an exactness bit, and encoding `0x20` in an export is malformed. This keeps exact `ref.func` sound across module boundaries. | `exact-func-import.wast` | T149, T152 |
| Allocation | Types with descriptors cannot be allocated by `struct.new` or `struct.new_default`. `struct.new_desc` / `struct.new_default_desc` consume an exact reference to the declared descriptor as the final operand; they produce an exact reference to the allocated type. Default allocation additionally requires defaultable fields. Allocation does not dynamically check an inexact descriptor. | `struct_new_desc.wast` | T153–T155 |
| Descriptor access | `ref.get_desc` obtains the descriptor reference associated with a value whose static type has descriptor metadata; the typing rule constrains the resulting descriptor type. Null and missing descriptor behavior follows the formal rule and cannot be inferred from JS examples. | `ref_get_desc.wast` | T153, T156 |
| Descriptor equality casts | `ref.cast_desc_eq`, `br_on_cast_desc_eq`, and failure-branch form compare the object’s descriptor relation with the requested type under the source’s cast rules. Nullability and branch stack effects follow their formal judgments. These are distinct from ordinary RTT subtype casts. | `ref_cast_desc_eq.wast`, `br_on_cast_desc_eq.wast`, `br_on_cast_desc_eq_fail.wast` | T153, T156 |
| Binary syntax | Subtype grammar adds descriptor prefix byte `0x4D` and describes prefix byte `0x4C`; exact heap types use prefix `0x62` followed by `u32`; exact function imports use `0x20` in the import external type. Descriptor instructions use GC prefix `0xFB`, subopcodes 32–38. Existing heap-type-immediate instructions accept exact heap types without changing their instruction encoding. | `binary-descriptors.wast`, `exact.wast`, and opcode-specific `.wast` cases | T149 |

The test filenames above name the pinned suite’s concepts; exact inventory can vary within that commit. Existing concrete files include `binary-descriptors.wast`, `array_new_exact.wast`, and `br_on_cast_desc_eq.wast`. T149 should resolve any filename mismatch against the pinned directory, not silently treat a missing test as passing.

## Excluded behavior and unresolved clauses

The proposal’s JavaScript prototype lookup, exported object `[[GetPrototypeOf]]`, `wasm:js-prototypes` import, `configureAll`, compile-option builtins, wrapper construction, error messages, and prototype construction/configuration are embedding APIs and excluded. Their prose does not add Core binary/type/validation behavior to this task.

The “Type Section Field Deduplication” section is exactly `TODO`; it specifies neither encoding nor semantics. Do not implement a deduplication encoding, accept one, or infer that field sharing/deduplication is required. Reconsider only after a refreshed authoritative source and reviewed task update. The pinned proposal also has TODOs for detail of JS errors and separating JS wrapper APIs; those belong exclusively to the excluded embedding API.

The explainer’s notes proposing alternatives (such as disallowing descriptor chains or permitting absent descriptors) are not adopted rules. The pinned formal grammar and judgments are the implementation contract. If those rules conflict with a concrete test, report the clause and test path as a blocking discrepancy; do not resolve it by guessing.
